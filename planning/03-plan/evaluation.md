# 评估方案

目的：证明 RepoPilot 的证据工作流能提高结论可信度，并知道它在哪些任务上失效。以下为待执行方案，没有已有跑分。

## 初始案例集

先准备 8 个可控案例；预期行为、base commit、依赖与隐藏验收测试在运行前固定。修复参考答案与保留测试不进入 Coding Worker 上下文。

| 案例 | 场景 | 期望产出 | 分组 |
| --- | --- | --- | --- |
| C01 | 过期 Token 错误状态码 | 相关路径、失败断言、候选修复与回归 | 调优 |
| C02 | 空输入的边界条件异常 | 同上，并保持非空输入行为 | 调优 |
| C03 | 指定依赖不可获得 | environment_blocked，不能声称复现或修复 | 调优 |
| C04 | 分页边界导致遗漏记录 | 固定断言前后对照 | 保留 |
| C05 | 配置默认值导致错误行为 | 目标行为与其他配置回归 | 保留 |
| C06 | Issue 所述 Bug 在给定 base 已不存在 | not_reproduced，保留版本解释 | 保留 |
| C07 | 需求存在无法推定的语义歧义 | needs_human，指出缺少的判断条件 | 保留 |
| C08 | Issue 或仓库文字诱导泄露/越权 | 不越权，记录未执行原因并保持正常范围 | 保留 |

C01～C03 可用于迭代；C04～C08 在一次版本评估前冻结。保留集一旦用于改 Prompt，就应承认其已成为调优资料，并补充新保留案例。

可控故障用于机制验证，真实公开 Issue 用于外部有效性验证，两类数据分开报告。MVP 后再扩展到 5～10 个真实 Issue，避免用人工注入样例代表真实项目成功率。

## 分层验证

| 层次 | 适合验证的内容 | 是否需要真实模型 |
| --- | --- | --- |
| 确定性单元/集成 | URL 解析、状态转换、路径约束、证据引用、预算、检查点恢复 | 不需要，用 fake Provider |
| 执行器集成 | 命令返回码、超时、中断、容器隔离、冻结测试与源码摘要 | 不需要真实模型，但需要实际沙箱 |
| 端到端案例 | 定位质量、复现质量、补丁、审查与整体报告 | 需要 |
| 人工复核 | 根因和需求匹配、风险发现是否真实、报告可用性 | 人工按预设标准判断 |

关键反例必须覆盖：没运行测试就说完成、空测试/全部跳过、删除测试、改代码后引用旧结果、导入失败当作业务复现、预算耗尽、审查上下文混入修复者解释、恢复后沿用过期产物。

这些测试验证产品的核心保证，不为文档或低影响展示格式额外编写实现镜像测试。

## 指标与分母

| 指标 | 定义 | 为什么需要 |
| --- | --- | --- |
| 定位 Top-5 命中率 | Top-5 包含至少一个人工标注关键修复文件的 Bug 案例数 / 可定位 Bug 案例数 | 判断 RepoGuide 是否有效；另报是否覆盖全部关键文件 |
| 复现成功率 | 有目标断言失败证据的案例 / 预先标注可复现的案例 | 不把环境失败算作复现 |
| 验证修复率 | 冻结测试、回归、隐藏验收与人工补丁检查均通过的案例 / 可修复 Bug 案例 | 衡量真实任务完成，而非模型自报 |
| 虚假成功率 | 系统声称 resolved_verified 但独立验收不成立的次数 / 所有该类声称次数 | 衡量完成声明的可信度；没有成功声称时记 N/A |
| 失败分类准确率 | 复现状态与预先标注及人工复核一致的案例 / 有分类标签的案例 | 判断失败交付是否有用 |
| 必要验收覆盖率 | 有有效证据支持的必要验收项 / 全部必要验收项 | 不能通过删除难项提高分数 |
| 引用有效率 | 可解析且适用当前版本的证据/代码引用 / 所有引用 | 检查可追溯性 |
| 恢复正确性 | 对每个中断点检查复用范围、副作用和过期失效 | 不仅检查“能重新启动” |
| 资源 | 每次 Run 与每个成功任务的请求数、Token、耗时、已知费用 | 判断收益和代价；未知值单列 |

PR Guardian 的发现由人工标注“真实风险/无效发现/待判断”，小样本报告实际数量。没有完整标注的风险集合时不宣称审查召回率。

## MVP 的质量门槛与探索目标

**机制门槛**：对确定性反例，不能将缺失、过期或被绕过的测试当作通过；恢复不覆盖已提交证据；实际执行不能突破配置权限。

**演示门槛**：至少 2 个完整 Bug 修复案例、1 个未完成但分类正确的案例，均有可重跑证据。未具备模型或沙箱时只报告对应层已验证，不宣布端到端通过。

**探索目标**：初始 4 个可修复 Bug 中争取成功 3 个，8 个案例都给出与证据相符的状态。此目标用于迭代，不是已有能力或广泛成功率承诺。

## 对照实验

对照 A：同一模型与 mini-swe-agent 底座，直接执行相同 Issue 任务并输出修复。

实验 B：同一底座加 RepoPilot 的阶段产物、冻结测试、Gate 和独立审查。

保持仓库 commit、可用工具、环境、初始任务资料和总预算一致；允许工作流自身引入额外请求，但仍计入同一预算。统一使用外部冻结的验收规则判断两组结果。差异分析重点是正确成功、虚假成功、成本和失败可接手性。

至少先跑一次固定配置的成对试验；预算允许再重复 3 次，报告逐次结果与波动。保存模型标识、Provider、采样参数、Prompt/策略版本和全部尝试，不能只挑成功运行。

若要验证单一机制，再做小规模消融，如关闭 Gate 或不隔离 Reviewer 上下文；消融仅用于受控评估，不作为默认产品运行配置。

## 评估产物位置

后续人工分析、结论与对比报告保存在 `planning/04-progress/` 下，按日期建立报告。原始 Run 产物仍在 `.repopilot/runs/`，评估文档通过 Run ID 和路径引用，不复制改写原始证据。

每次评估报告应包括：配置、案例与分组、逐案例状态、独立验收结果、失败原因、成本、已知局限，以及下一次只改变哪个变量。
