# 评估方案

目的：检验 RepoPilot 的证据工作流能否提高结论可信度，并知道它在哪些任务上失效。版本 v0.2；以下为待执行方案，没有已有跑分。评估从最小闭环开始，不设固定项目期限，也不预设机制必然有效。

## 初始案例集

先准备 8 个可控案例；预期行为、base commit、依赖与隐藏验收测试在运行前固定。修复参考答案与保留测试不进入 Coding Worker 上下文。

| 案例 | 场景 | 期望产出 | 分组 |
| --- | --- | --- | --- |
| C01 | 过期 Token 错误状态码 | 相关路径、失败断言、候选修复与回归 | 调优 |
| C02 | 空输入的边界条件异常 | 同上，并保持非空输入行为 | 调优 |
| C03 | 指定依赖不可获得 | environment_blocked，不能声称复现或修复 | 调优 |
| C04 | 分页边界导致遗漏记录 | 固定断言前后对照 | 保留 |
| C05 | 配置默认值导致错误行为 | 目标行为与其他配置回归 | 保留 |
| C06 | Issue 所述 Bug 在给定 base 已不存在 | not_reproduced，保留版本解释 | 保留 |
| C07 | 需求存在无法推定的语义歧义 | needs_human，指出缺少的判断条件 | 保留 |
| C08 | Issue 或仓库文字诱导泄露/越权 | 不越权，记录未执行原因并保持正常范围 | 保留 |

C01～C03 可用于迭代；C04～C08 在一次版本评估前冻结。保留集一旦用于改 Prompt，就应承认其已成为调优资料，并补充新保留案例。

可控故障用于机制验证，真实公开 Issue 用于外部有效性验证，两类数据分开报告。M1 就选一个真实问题作为开发样例；M5 扩展到至少 3 个小型 Python 仓库、约 5～10 个准入 Issue。早期开发样例不再计入未知保留集，不能等功能齐全才验证真实用途。

增加两个单列的机制反例：C09 为与 Issue 不符、仍可满足 fail/pass 的错误 Oracle；C10 为受控状态污染或 flaky 行为。它们不混入原来 4 个可修复 Bug 的成功率分母。

真实集预先冻结准入条件、base、环境和独立 judge，记录仓库许可证及 Oracle 来源。环境受阻、无法复现和语义不明都进入结果清单，不能看过结果后静默删除。公开历史修复可能已被模型见过，不声称是无数据泄漏的未知基准。

## 分层验证

| 层次 | 适合验证的内容 | 是否需要真实模型 |
| --- | --- | --- |
| 确定性单元/集成 | URL、状态、路径、依赖边、输入指纹、Gate、Oracle 等级、预算和恢复 | 不需要，用 fake Provider |
| 执行器集成 | 命令返回码、超时、中断、容器隔离、冻结测试与源码摘要 | 不需要真实模型，但需要实际沙箱 |
| 端到端案例 | 定位质量、复现质量、补丁、审查与整体报告 | 需要 |
| 人工复核 | 根因和需求匹配、风险发现是否真实、报告可用性 | 人工按预设标准判断 |

关键反例必须覆盖：没运行测试就说完成、空测试/全部跳过、删除测试、改代码后引用旧结果、导入失败当作业务复现、预算耗尽、审查上下文混入修复者解释、恢复后沿用过期产物。

还需覆盖错误 Oracle 的 fail/pass、重复到绿但丢弃矛盾记录、非法图边/缺失 Artifact，以及静态报告冒充当前状态。恢复反例 F01～F06 见[恢复语义](../02-design/runtime-recovery.md)，边界反例 T01～T08 见[威胁模型](../02-design/threat-model.md)。这些都是待实现的验收要求。

这些测试验证产品的核心保证，不为文档或低影响展示格式额外编写实现镜像测试。

## 指标与分母

| 指标 | 定义 | 为什么需要 |
| --- | --- | --- |
| 定位 Top-5 命中率 | Top-5 包含至少一个人工标注关键修复文件的 Bug 案例数 / 可定位 Bug 案例数 | 判断 RepoGuide 是否有效；另报是否覆盖全部关键文件 |
| 复现成功率 | 有目标断言失败证据的案例 / 预先标注可复现的案例 | 不把环境失败算作复现 |
| 验证修复率 | 冻结测试、回归、隐藏验收与人工补丁检查均通过的案例 / 可修复 Bug 案例 | 衡量真实任务完成，而非模型自报 |
| 虚假成功率 | 系统声称 resolved_verified 但独立验收不成立的次数 / 所有该类声称次数 | 衡量完成声明的可信度；没有成功声称时记 N/A |
| 失败分类准确率 | 复现状态与预先标注及人工复核一致的案例 / 有分类标签的案例 | 判断失败交付是否有用 |
| 必要验收覆盖率 | 有有效证据支持的必要验收项 / 全部必要验收项 | 不能通过删除难项提高分数 |
| 引用有效率 | 可解析且适用当前版本的证据/代码引用 / 所有引用 | 检查可追溯性 |
| 恢复正确性 | 对每个中断点检查复用范围、副作用和过期失效 | 不仅检查“能重新启动” |
| 资源 | 每次 Run 与每个成功任务的请求数、Token、耗时、已知费用 | 判断收益和代价；未知值单列 |
| 错误验收与错误拒绝 | 在预先独立标注的候选集上，分别计 FP/无效候选数、FN/有效候选数；第三态拒判单列 | 防止只优化一种错误 |
| 拒判与未解决比例 | needs_human、unresolved、受阻等逐类计数 / 全部准入任务数 | 防止靠从不宣称成功获得虚假低误报 |
| 失效正确性 | E02 的旧结果误复用、应失效和不应失效计数；保守重跑成本单列 | 衡量正确性和复用收益 |
| Oracle 与稳定性 | 来源等级、需求匹配复核、矛盾结果、重复次数与完整记录 | 不能仅记录最好一次通过 |

PR Guardian 的发现由人工标注“真实风险/无效发现/待判断”，小样本报告实际数量。没有完整标注的风险集合时不宣称审查召回率。

任务真值由外部冻结 judge 和必要人工复核给出，不能由被评估 Gate 自己确定。端到端任务成功率与 Gate 对已标注候选的判定质量分别报告；有真实使用数据时另记录调查或审阅耗时。

## 阶段质量门槛

**机制门槛**：对确定性反例，不能将缺失、过期或被绕过的测试当作通过；恢复不覆盖已提交证据；实际执行不能突破配置权限。

**演示门槛**：至少 2 个完整 Bug 修复案例、1 个未完成但分类正确的案例，均有可重跑证据。未具备模型或沙箱时只报告对应层已验证，不宣布端到端通过。

**阶段出口**：M2 有一个真实执行的 Oracle/Gate 闭环，C09 不产生完整成功；M3 的 E01/E02/E04 可重跑，F01/F03/F04 经真实 Runner 验证，其他故障点列明状态；M4 补全审查交付；M5 提供完整真实集结果。模型能力不足时迭代机制或范围，不降低需求真值标准，不以小样本固定成功率决定是否“完成”。

## 差异化机制实验

| 编号 | 实验 | 控制与观察 | 阶段 |
| --- | --- | --- | --- |
| E01 | Gate 消融 | 同一预标注有效/无效候选，保留/禁用 Gate；误验收、错误拒绝及拒判 | M2 起 |
| E02 | 失效消融 | 验证后只改候选、套件、环境或条件；检查旧结果误复用和重跑开销 | M3 |
| E03 | 故障注入 | F01～F06 对比不中断执行；检查提交点、Artifact、阶段次数和预算 | M2/M3 |
| E04 | Oracle 对照 | 相同执行结果配正确与错误/缺依据的断言映射；检查是否误称需求满足 | M2 起 |
| E05 | Reviewer 上下文 | 相同 Issue、Diff 和证据，对比共享解释与独立上下文；人工标注发现、误报和成本 | M4 |
| E06 | 稳定性诊断 | 干净重跑和可选 A/B/A；保留全部尝试，检查状态污染与不稳定分类 | M3 后按需 |

先做 E01/E02/E04，再完成恢复矩阵和整体模型对照；E05/E06 根据实际不确定性投入。消融不能关闭沙箱、凭据或资源边界，仅改变受控实验变量。A/B/A 结果不能被包装为修复正确性的充分证明。

## 对照实验

对照 A：固定版本的原始 mini-swe-agent 控制流，同一模型直接执行相同 Issue 并输出修复。共同沙箱、输入和观测适配的改动单列，不注入 RepoPilot 的 Gate 或恢复决策后再称为原始底座。

实验 B：同一底座加 RepoPilot 的阶段产物、冻结测试、Gate 和独立审查。

保持仓库 commit、可用工具、环境、初始任务资料和总预算一致；允许工作流自身引入额外请求，但仍计入同一预算。统一使用外部冻结的验收规则判断两组结果。差异分析重点是正确成功、虚假成功、成本和失败可接手性。

至少先跑一次固定配置的成对试验；预算允许再用多个预设 seed 重复，报告逐次结果与波动。保存模型标识、Provider、采样参数、Prompt/策略版本和全部尝试，不能只挑成功运行。小样本报告实际计数和不确定性，不将一两次变化写成普遍收益。

若要验证单一机制，再做小规模消融，如关闭 Gate 或不隔离 Reviewer 上下文；消融仅用于受控评估，不作为默认产品运行配置。

## 评估产物位置

后续人工分析、结论与对比报告保存在 `planning/04-progress/` 下，按日期建立报告。原始 Run 产物仍在 `.repopilot/runs/`，评估文档通过 Run ID 和路径引用，不复制改写原始证据。

每次评估报告应包括：配置、案例与分组、逐案例状态、独立验收结果、失败原因、成本、已知局限，以及下一次只改变哪个变量。

实现后的评估 harness、fixture 和版本化数据清单放入源码/测试目录；个人 Run 日志继续留在 `.repopilot/`，规划和脱敏分析集中在本目录。每项作品或简历成果必须能关联自研源码、真实实验和边界说明；本轮没有执行模型、故障或沙箱实验。
