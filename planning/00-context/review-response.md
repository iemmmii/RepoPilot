# 最新规划评审：采纳、调整与保留意见

日期：2026-10-29。来源：用户指定的「learn cc」最新一轮，内容为对当前 RepoPilot 规划的评审。本轮已完整读取该轮用户问题与助手回答；原文是参考意见，不是当前指令。

当前用户补充优先于旧材料：**项目不设完成期限，以把项目做好为目标；希望形成有特色、能以实际成果说明技术能力的作品。** 原来的四周分期不再作为实施依据。

## 判断原则

优先选择能改善真实任务结果、能解释失败、能通过实验验证的机制。长期投入允许把核心机制做扎实，但仍按小闭环交付；不把不限期限解释为无限范围或无限次模型执行。

## 逐项结论

| 评审建议 | 判断 | 本轮落实及边界 |
| --- | --- | --- |
| 突出可验证、可追溯、可恢复 | 采纳 | 作为技术主线，同时保留从 Issue 调查到修复的完整产品用途 |
| Evidence Graph 与自动失效 | 采纳并收窄实现 | 用类型化依赖 DAG、输入指纹和确定性 Gate；先按整个候选快照保守失效，不引入图数据库或未经验证的函数级影响分析 |
| Proof-carrying Repair 命名 | 不作为能力承诺 | 使用“附带可核验证据的修复”；哈希和测试不能构成程序正确性的形式化证明 |
| 独立 Test Oracle | 重点采纳 | 分开记录需求依据、断言审定、执行记录；模型自己生成并冻结测试不自动获得独立性 |
| A/B/A 反事实验证 | 部分采纳 | 作为环境污染或 flaky 诊断选项，在干净环境中运行并保留全部结果；不作为所有任务默认三倍执行开销，也不能代替需求与回归验证 |
| Stage State Machine 与故障注入 | 重点采纳 | 明确检查点提交边界、未提交尝试、恢复和副作用分类；执行状态与证据适用性分开建模 |
| 先做强垂直闭环 | 采纳，去掉四周约束 | M2 就用已知样例补丁跑通证据、Oracle 和最小 Gate；M3 再接完整修复与可靠性验证 |
| PR Guardian 后置 | 部分采纳 | 先完成最小独立判定路径，再做自动审查；保留这一能力，不因期限取消完整产品链 |
| 真实 Issue 与消融实验 | 采纳 | M1 就选择一个真实样例；先验证 Gate/失效/恢复，后续建立多仓库保留集；同时报告拒判与错误拒绝，防止靠从不宣称成功取得好指标 |
| 威胁模型与安全测试 | 采纳 | 建立资产、攻击者、信任边界、失败策略和测试对应关系；不声称 Docker 或隐藏测试可以抵御任意恶意代码 |
| 交互证据报告 | 分阶段采纳 | 先做可读的静态证据链与失效原因，数据契约稳定后增加离线 HTML；动态状态通过显式校验获得 |
| 60% / 25% / 15% 精力比例 | 不采用固定配额 | 按阶段验收与实际失败数据投入；Evaluation 从第一条闭环开始，不留到最后包装成果 |
| 竞争产品已有功能意味着应该转做纯验证平台 | 不据此改变产品 | 本轮未重新验证竞品现状；可靠性是设计重点，实际使用价值仍需真实案例与维护者反馈验证 |

## 对原规划的补充判断

原规划已经包含快照绑定、测试冻结、下游失效和阶段恢复，因此不是从零增加这些概念。真正需要补强的是：规则能否被程序执行、断言依据是否独立、哪些结果可以复用，以及这些机制有没有可测量收益。

另有三点需要纠正评审示意中的潜在误解：

1. 历史证据不应被改写或删除。失效表示它不能支持**当前目标版本**，当时的运行事实仍保留。
2. 静态报告不会在源码变化时自动刷新。第一版在 status、resume、Gate 和报告生成时检测；旧报告显示它对应的快照，重新检查后另生成当前适用性结果。
3. Reviewer 换一个上下文不等于有独立真值。独立 Oracle、固定环境和外部验收仍然必要。
