# 分阶段实施计划

以下是范围分期，不是已经开始执行的日程。实施状态统一查看 [进度台账](../04-progress/progress.md)。

## M0：需求与设计基线

交付：最后 5 轮来源、需求提炼、产品边界、架构、证据契约、里程碑、评估计划和维护约定。

完成条件：来源可追溯；用户要求与默认建议区分；明确首个闭环与下一步；文档全部在 `planning/`。

## M1：只读调查闭环（参考第 1 周）

目标：输入 Issue URL 或本地 Issue JSON，输出有真实代码引用的调查报告。

| ID | 任务 | 交付与验证 |
| --- | --- | --- |
| P1-01 | 适配与环境小实验 | 确认容器路线；选一个受控 Python 样例；核对 mini-swe-agent v2 的模型、执行、终止和日志接口；记录可行性与版本 |
| P1-02 | 建立项目骨架与最小契约 | CLI、配置、Issue/Run/Artifact 数据模型；选定 Python 版本及依赖锁；文档与代码目录分离 |
| P1-03 | Issue 只读读取 | URL 解析、API 错误与限流分类、本地 JSON 导入；不要求离线测试访问 GitHub |
| P1-04 | 仓库版本与代码检索 | 固定 base SHA；文件过滤、rg/AST、相关路径与符号；检查代码引用有效性 |
| P1-05 | RepoGuide 调查与报告 | 事实/假设/候选命令分开；Top-5 文件依据；保存 issue、repo_context、investigation 产物 |
| P1-06 | 最小状态存储和 CLI 验收 | 检查点与状态查询；模拟 Provider 的离线测试；至少一个真实模型调查样例 |

验收场景：正常 Issue、非法 URL、Issue 不可用、空仓库或不支持的项目类型、模型结构化输出错误。能输出未完成原因，不能编造文件位置。

M1 出口：至少一个可控 Issue 得到可读报告，报告引用均存在且绑定 commit；目标仓库源码没有被修改。测试命令只作为候选显示。

P1-01 的容器实验若暂时受阻，允许先完成只读调查；M2 不能绕过沙箱进入宿主执行。

## M2：隔离复现（参考第 2 周）

目标：在固定环境与 base 上尝试复现，交付真实失败证据及明确分类。

| ID | 任务 | 交付与验证 |
| --- | --- | --- |
| P2-01 | SandboxRunner 与权限策略 | 固定镜像、非特权、资源/时间/网络约束；只挂载目标源码，证据目录与凭据不可写不可读 |
| P2-02 | 可信命令证据 | 命令、工作目录、时间、返回码、终止原因、日志引用、源码与环境标识；验证超时和中断 |
| P2-03 | 复现断言生成与冻结 | 形成能对应 Issue 的测试；固定套件哈希；在 base 执行并核对失败原因 |
| P2-04 | 复现分类与报告 | 区分 reproduced、not_reproduced、environment_blocked、needs_human；报告保留可接手信息 |
| P2-05 | 阶段恢复与初始评估集 | 断点处不重复已提交阶段；输入变化令下游过期；建立 3 个调优案例并记录结果 |

M2 出口：一个已复现案例、一个未复现案例、一个环境受阻案例有正确分类与真实命令证据；中断后可从可靠阶段继续。

两周范围到此形成独立可交付版本：调查 + 复现 + 证据报告。修复能力延后时，这个版本仍可作为作品演示。

## M3：候选修复与确定性验收（参考第 3 周）

目标：生成可审阅补丁，并证明固定目标行为在 base 失败、在候选通过。

| ID | 任务 | 交付与验证 |
| --- | --- | --- |
| P3-01 | 仓库副本与补丁管理 | managed worktree、受限源码副本、候选摘要；导出变更时校验范围并保存 Diff |
| P3-02 | 接入 Coding Engine | mini-swe-agent 适配；统一记录动作、正常退出、异常和全局预算；引擎 Submitted 不直接表示验收通过 |
| P3-03 | 冻结测试的前后对照 | 同一套件在 base 和候选执行；加入指定回归集；检查收集数、目标测试与跳过状态 |
| P3-04 | CompletionGate 与有限返工 | 拒绝过期证据、删除/改弱测试、空测试、预算伪成功；修复轮数与总预算同时生效 |
| P3-05 | 本地修复闭环 | 至少 2 个可控 Bug 形成真实前后对照；不成功案例保存 Diff 与未完成原因 |

M3 出口：本地 Diff、失败/通过记录和回归结果绑定同一候选；原工作区保持可用；没有远程写入。

## M4：独立审查、交付与评估（参考第 4 周）

目标：让用户能从报告理解每个结论的依据与局限。

| ID | 任务 | 交付与验证 |
| --- | --- | --- |
| P4-01 | PR Guardian | 独立上下文、只读候选、结构化发现；候选改变后审查失效；关键发现能阻断完成判断 |
| P4-02 | 验收覆盖表 | 需求来源、验证方法、证据 ID 与状态；保留未验证、受阻和需人工判断项 |
| P4-03 | 统一报告与 PR 草稿 | Issue → 定位 → 复现 → Diff → 验证 → 审查的证据索引；导出本地 PR 标题和描述 |
| P4-04 | 对照评估与失败分析 | 执行调优/保留案例；记录真实成功率、虚假成功、成本和耗时；归类失败并给出一次有数据的改进 |
| P4-05 | 演示与使用材料 | 可重复演示、环境说明、已知边界；外部反馈作为后续产品验证任务 |

M4 出口：至少 2 个完整修复演示，加至少 1 个诚实失败演示；评估报告区分测试结果、模型结论和人工判定。模型能力未达预期时交付可解释结果，不降低验收定义。

## 关键依赖顺序

```text
证据字段与版本绑定
  → 可用执行环境和可信记录
  → 固定的复现断言
  → 候选修改
  → 前后对照与回归
  → 独立审查和覆盖表
  → 全链路报告与对照实验
```

状态存储在 M1 建立最小版本，M2 验证恢复，避免最后再补。评估样例在 M1 就选择，M2 开始记录，M4 汇总而非临时挑成功案例。

## 执行时的前 3 个工作单元

1. **可行性记录**：核验容器、一个模型接口和底座 v2，选定演示样例，形成明确结果；记录失败条件及只读降级路线。
2. **最小输入输出**：Issue JSON → 版本固定的仓库摘要 → Run 目录 → 调查报告；先用离线 Provider 测试骨架。
3. **真实调查**：接入 Issue URL 和一个真实模型调用，对照已知相关文件检查报告依据。

每个单元完成后更新进度台账，不提前标记依赖它的任务完成。

## 范围收缩顺序

时间不足时先去掉 UI、MCP 接入、多 Provider、复杂缓存与自动重试。仍不足则先交付 M2 版本，将修复与审查延后。证据真实性、执行隔离和明确失败分类始终保留。

暂不安排：向量库、常驻多 Agent 团队、分布式任务队列、账号计费、自动远程 PR、生产托管服务。出现真实需求后在决策记录重新评估。
