# 设计决策与待验证事项

记录日期：2026-10-29。`用户要求` 表示当前会话已有依据；`默认方案` 表示本轮提出的可调整选择；`待实验` 表示实现前须核验的假设。

## D-001：规划材料集中到 planning/

状态：用户要求；“文件内再分文件夹”按独立目录解释。

原因：需要长期保存分析、规划与进度，并与代码隔离。入口为 `planning/README.md`，执行状态唯一来源为进度台账。未来运行证据使用 `.repopilot/`，通过文档引用。

## D-002：围绕 Issue 验收组织三个能力

状态：默认方案，依据最新对话方向。

选择：RepoGuide 提供代码理解，IssueRepro 提供失败证据，Coding Worker 生成补丁，PR Guardian 做独立审查。整个产品以验收覆盖和可接手成果组织交付。

考虑过的路线：通用仓库聊天助手、单独复现工具、三个互相聊天的独立窗口。当前选择能形成完整任务链，同时允许在调查和复现阶段独立交付。

## D-003：单一底座 + 自有工作流与证据层

状态：mini-swe-agent v2 为首选，适配可行性待实验。

理由：符合二次开发意愿，便于把时间投入差异化功能，也保留研究 Harness 的入口。只在薄适配层无法满足需求时做小范围 Runtime 修改。

替代方案：从零重写全部 Agent Runtime，或选更完整的 SDK。前者会延后产品闭环，后者扩大初始理解和集成范围。M1 实验失败时重新比较，不能因已经写在规划里就强行接入。

上游版本参照见[调研记录](../00-context/research-notes.md)；尚未安装或锁定依赖。

## D-004：顺序工作流与独立上下文

状态：默认方案。

理由：定位、复现、修复和审查存在依赖，顺序阶段更便于调试、恢复与评估。同一模型可承担多个角色，Reviewer 的上下文单独构造。

暂缓常驻 Agent Teams。只有出现可并行的独立任务且实验收益足够时，再引入并发协作。

## D-005：先 CLI、Python/pytest 和小型公开仓库

状态：默认方案。

理由：缩小环境和语言差异，保证验收可自动执行。先完成只读调查，调查/复现可独立交付；原来的两周参考已由 D-012 的无固定期限路线覆盖。

暂缓 UI、多语言、私有仓库和分布式部署。模型型号和 Provider 不在本轮强制绑定。

## D-006：确定性 Gate 优先，语义审查补充

状态：默认方案，来自 Goal Loop 学习背景与证据定位。

理由：返回码、版本、文件哈希和测试是否执行可由程序检查；行为合理性和风险仍需要模型或人工。独立模型不能把缺失证据变成成功。

不将“模型停止调用工具”“引擎 Submitted”“报告生成完成”直接等同于问题解决。

## D-007：源码修改隔离与执行隔离分别落实

状态：默认方案；当前容器可用性待实验。

选择：Git Worktree 管理候选，容器执行受限源码副本，控制面保存证据和凭据。无可用沙箱时只读降级。

理由：源码副本只能避免主工作区混乱，无法限制进程访问、网络或凭据。第一版目标是可控样例，不扩展为任意恶意代码托管平台。

## D-008：文件式阶段产物与阶段恢复

状态：默认方案。

理由：单任务条件下，原子 manifest、不可覆盖的阶段产物与事件日志足以展示恢复能力，且容易检查。JSONL 不承担无需实现的分布式一致性保证。

重跑前检查输入摘要；恢复粒度先到阶段。出现并发和检索需求后评估 SQLite，不先上队列或数据库集群。

## D-009：GitHub 先读取，交付先本地

状态：默认方案。

选择：产品第一版使用窄接口读取 Issue；生成本地 PR 草稿。GitHub MCP 留作后续连接适配，远程发布不属于本次实现范围。

理由：先验证核心价值，减少权限与副作用管理范围。历史助手提出过的远程发布确认方式仅为参考；未来远程动作根据当时用户实际授权处理。

## D-010：用对照案例评价差异化

状态：默认方案。

选择：受控案例调优 + 保留集 + 同模型同底座对照。核心观察为验证修复率、虚假成功、失败报告质量与资源消耗。

理由：只有数据才能说明证据层与独立审查是否有帮助。少量可控案例通过后，再做真实维护者试用；不将技术演示当成市场验证。

## D-011：建立规范的 Git 基线与协作流程

状态：用户要求规范版本控制并上传规划；具体流程为本轮执行约定。

选择：连接用户指定的 RepoPilot 仓库，空仓库首次基线提交到 main；后续采用短期分支、PR、Conventional Commits 与可回退的主干历史。增加忽略规则、文本换行规范和 PR 模板，细则见[版本控制规范](version-control.md)。

原始个人对话快照保留本地，版本库保存提炼后的规划；运行数据与凭据不入库。本轮不创建产品发布标签，不将流程文档等同于已配置的服务端分支保护。

## D-012：取消固定期限，按质量出口推进

状态：用户明确要求项目不限定四周完成。

选择：M1～M5 按运行基础、最小验证、可靠修复、完整审查交付、真实有效性推进。保留原有 21 个任务 ID，新增 10 项质量任务，不把未实现能力标记完成。旧文档中的周数仅作为历史，不再约束执行。

不采用固定精力比例，也不因长期投入而预先加入所有框架和功能。单次 Run 仍受预算、权限与停止规则约束。

## D-013：采用轻量证据 DAG 与保守失效

状态：默认设计；实现与收益待实验。

选择：类型化依赖、输入指纹、当前适用性与不可覆盖历史。先按整个候选快照失效，不上图数据库、函数级精准缓存或后台监听。静态报告绑定历史版本，当前状态由显式校验得出。

理由：关键问题是漏失效和错误复用，而非图的展示形式；哈希只能验证一致性，不能推出语义正确。细则见[证据图](../02-design/evidence-graph.md)。

## D-014：Oracle 审定与执行证据分别建模

状态：默认设计；对评审中“冻结不等于正确”的重点采纳。

选择：断言有独立需求依据和审定状态；provisional Oracle 不支持完整成功。保留 candidate_verified 范围结论、独立 judge 与必要人工判定；模型换上下文不自动获得真值。

A/B/A 按需诊断，所有尝试入账，不是默认三倍执行或正确性证明。不采用“Proof-carrying Repair”作为形式化保证。细则见[证据契约](../02-design/evidence-contracts.md)。

## D-015：明确检查点语义并用故障注入验收

状态：默认设计，待实现。

选择：manifest 成功替换为可靠提交点；未引用产物为 orphan；执行状态与 stale 适用性分离。以 F01～F06 验证进程中断，不承诺 exactly-once、任意断电或分布式事务。

理由：恢复必须说明哪些事实可复用，不能只演示重新启动。安全和可信边界见[恢复语义](../02-design/runtime-recovery.md)及[威胁模型](../02-design/threat-model.md)。

## D-016：用机制实验和真实结果支撑技术特色

状态：默认设计，待执行。

选择：先验证 Gate/失效/Oracle/恢复反例，再扩展原底座对照、审查上下文和多仓库真实集。同时报告真实修复率、虚假成功、错误拒绝、拒判与成本，避免“从不接受”造成指标幻觉。

保留 Issue 到修复的产品用途，不仅为简历改造成纯验证框架。CLI 和静态证据链优先，离线 HTML 后续完善；只用实际源码和实测数据描述成果。完整取舍见[评审回应](../00-context/review-response.md)。
